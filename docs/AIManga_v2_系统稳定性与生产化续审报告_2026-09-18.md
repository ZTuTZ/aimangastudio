## 1. 审计结论与边界

Phase 8 已经加入 Stage Item attempt token、提交事务、执行范围、Task 租约、暂停状态、Worker 平滑缩容和 Flyway，但这些能力之间仍有接缝。当前不宜据提交标题判断“生产化已经完成”。

本轮整理了 **24 项优先修复问题（2 项 P0、22 项 P1）和 6 项 P2 完善建议**。最先需要处理的是：

1. `TaskMapper` 查询注解挂错方法，MyBatis 注册时出现冲突，阻断正常初始化。
2. `CHAPTERS` 仍然使用全项目 Runner，LAYOUT 还会误清理非目标话的 Items。
3. 去重复用任务没有同步新的 scope，与本次加入的固定范围 Runner 不兼容。
4. fencing 保护成功结果的主路径，但没有覆盖失败状态、Task 进度及部分非 Item 业务写入。
5. 暂停恢复会重新 force reset 已完成的内容；脚本更新后的 SUCCESS Item 又可能完全不重跑。
6. `CLEAN` 和 `REPAINT` 均错误执行上色。
7. 图片生成转存、实际批量导出、Redis 故障恢复仍未达到 Phase 8 的生产化目标。

### A01 — TaskMapper 注解冲突，阻断初始化

**位置**：`server/src/main/java/com/aimanga/v2/repository/TaskMapper.java:87`、`:104`、`:111`；调用方 `service/TaskService.java:89`。

`SELECT COUNT(*) ...` 的 `@Select` 与后插入的 `@Update` 都挂在 `pauseTask()` 上；原本应该使用该查询的 `countFiltered()` 已经没有 SQL 注解。

本轮提取当前这段注解和方法，用本地 MyBatis 3.5.16 注册最小 Mapper，实际得到：

```text
org.apache.ibatis.builder.BuilderException:
Detected conflicting annotations ... Select ... and ... Update ... on ... pauseTask
```

这是 Mapper 注册层的确定性错误。它可以导致正常 Spring/MyBatis 初始化失败；本轮未启动完整后端，不能把此探针描述为完整应用启动测试。即便只删除 `pauseTask` 上的查询注解，任务分页计数仍会缺少映射。

**建议**：将 COUNT 查询注解移回 `countFiltered()`，`pauseTask()` 只保留更新注解；增加真实 Mapper 注册检查。

**验收**：实际 `TaskMapper` 注册成功；任务分页过滤计数可执行；暂停 SQL 可执行；应用上下文启动检查通过。

### A02 — CHAPTERS 仍扩大范围并误清理 LAYOUT Items

**位置**：`pipeline/BatchTaskHandler.java:67`、`:113`、`:120`、`:209`。

仅 `scope=CHAPTER` 被识别为局部 Runner。`CHAPTERS` 虽然选出了目标话页面，执行时却使用 `StageRunScope.all()`；LAYOUT 同步还把它当成 `projectWide=true`。

**触发**：项目包含话 1、2、3，分别已有 LAYOUT Items；选择话 1、2 发起 CHAPTERS。非目标话 3 的 LAYOUT Item 被 orphan cleanup 删除。IMAGE 阶段也可能领取其他话的 PENDING Item。

**建议**：严格规范化 scope；CHAPTER 和 CHAPTERS 均生成目标页 Scope；只有明确的 PROJECT 请求执行项目级 orphan cleanup。入口拒绝未知 scope 和不完整的 ID 集合。

**验收**：两种出图模式下，多话 BATCH 只调用目标页面；其他话的 Item 主键、状态、结果和 retry_count 均保持不变。

### A03 — 局部任务项目级重置 FAILED

**位置**：`pipeline/BatchTaskHandler.java:220`、`:240`；`pipeline/LayoutTaskHandler.java:136`；`pipeline/PipelineStageService.java:239`。

Runner 的领取 Scope 并不能限制同步阶段的修改。当前局部 BATCH、按话布局和单页布局依然调用项目级 `resetFailedItems(projectId, stage)`，把范围之外的失败单元改为 PENDING。

单页 LAYOUT 的 `syncItems(project, chapterId, ...)` 也没有 pageId 过滤，可以为同项目其他缺布局的页面新增 Items。即使没有马上调用 AI，其他范围的状态已经被改变。

**建议**：同步、失败重置、force reset 和领取使用同一个规范化范围；增加限定 businessType/businessIds 的失败重置方法。

**验收**：局部操作前后，范围之外 FAILED 保持 FAILED，且单页操作不为无关页面新增 Item。

### A04 — 空 Scope 被解释成全项目

**位置**：`pipeline/StageRunScope.java:24`、`:45`；`pipeline/PipelineStageService.java:348`；`pipeline/LayoutTaskHandler.java:75`。

`pages(empty)` 返回 `all()`，`isUnbounded()` 也把空资产/章节集合视作无限范围。Service 和 Mapper 查询层又对空 ID 集合省略限制。

**触发**：按话 LAYOUT 的目标话没有页面，但项目其他话有 PENDING Item。目标页集合为空，却执行全项目。通过当前通用任务入口提交带有效 pageId 和无页面 chapterId 的 LAYOUT payload，也可到达这个分支。

隔离探针实际输出：

```text
empty pages unbounded=true
empty assets unbounded=true
```

**建议**：只有显式 `all()` 才表示全量；局部空集合表示“不执行”，或在入口返回 400；SQL 层也应拒绝空范围扩大查询。

**验收**：空局部范围产生零次领取、零次 AI 调用、零次非目标修改。

### A05 — 固定 Scope 与旧 Task 复用不兼容

**位置**：`controller/PageController.java:65`、`:83`、`:194`；`pipeline/MaterialGenerationService.java:94`；`service/TaskService.java:292`；`pipeline/SheetTaskHandler.java:77`；`pipeline/PageTaskHandler.java:64`。

`ensureUniqueActiveTask()` 只复用已有 Task，不合并 payload。以前“Runner 自动领取新增 Item”的注释依赖无范围执行；现在 Runner 使用从原 payload 构建的固定 Scope。

**触发示例**：

- 同一话页面 A 的 PAGE Task 运行时点击页面 B：B Item 被重置为 PENDING，但返回 A 的 Task，A Runner 不允许领取 B。
- 先生成角色集合 A，再勾选集合 B：素材入口返回旧 SHEET Task，但 B 不在原资产 Scope。
- COLORIZE/CLEAN/REPAINT 的去重按项目和类型，其他页的新 payload 同样不会加入原 Task。
- CHAPTERS 使用项目级去重槽，第二次不同的话集合也可能被静默替换为旧请求。

**建议**：选择并统一策略：不同 scope/参数建立独立请求并串行执行，或明确支持追加范围并持久化新的执行集合。参数不同且无法合并时返回可解释的冲突，不能提示创建成功却丢弃请求。

**验收**：连续发起不同目标/颜色/遮罩的请求，每个请求均有明确结果；无“接口成功但 Item 永久 PENDING”。

### A06 — 拿 Stage 锁之前破坏存活 Attempt

**位置**：`pipeline/PipelineStageService.java:272`；`controller/PageController.java:61`、`:77`；`pipeline/MaterialGenerationService.java:95`；`pipeline/PageTaskHandler.java:54`；`pipeline/ConcurrentStageRunner.java:103`。

Controller 和 Handler 在 Runner 获取 Stage 锁之前 force reset，且该 SQL 没有排除 RUNNING 状态，会清掉存活 Attempt 的 token。新任务随后可能因为拿不到锁而失败，旧请求则失去提交权；Stage 的 `markRunning()` 也发生在锁之前。

**触发**：BATCH 正在生成页面 A，用户点击 A 的重生成。旧 AI 请求仍在消耗费用，但 Item 已被重置。重复素材点击也可产生同类问题。

**建议**：在统一的锁和状态协议内接纳请求；重生成意图与当前执行 Attempt 分开保存。需要接管时显式撤销旧所有权并安排后续执行，不在失败的竞争请求里直接破坏旧 Attempt。

**验收**：被拒绝的竞争请求不改变旧 Attempt；接受的新请求有执行者；暂停中的 Stage 不会因另一个请求的 markRunning 而被隐式恢复。

### A07 — 失败写入没有 fencing

**位置**：`pipeline/PageGenerationService.java:68`、`:88`；`pipeline/SheetTaskHandler.java:130`、`:134`；`pipeline/AssetRefTaskHandler.java:123`、`:127`。

页面 GEN_RUNNING/GEN_FAILED 和资产 GEN_RUNNING/GEN_FAILED 使用普通 `updateById`。尤其 SHEET/ASSET_REF 在 fenced commit 被拒后抛 `StaleCommitRejectedException`，又被自身的通用 catch 捕获，直接把资产改成 FAILED。

**触发**：Attempt B 已提交最新图片并设置资产为空闲；旧 A 晚返回，fencing 正确拒绝 A 的成功提交，但 A 的 catch 随即把 B 的资产状态改成 FAILED。页面旧请求晚失败也会覆盖最新 GEN_SUCCESS，并用旧历史快照更新 records。

**建议**：所有执行相关的正式状态写入都校验当前 ownership；stale attempt 单独退出，不进行失败业务写入。失败历史记录也必须绑定正确的 Attempt。

**验收**：B 成功后 A 晚成功、晚失败、提交被拒，都不会改变 B 的状态、URL、错误和历史。

### A08 — Task 所有权失效后旧 Worker 仍能写入

**位置**：`task/TaskRuntime.java:69`、`:88`；`task/TaskRunner.java:80`；`pipeline/StageItemCommitService.java:58`；`pipeline/SplitTaskHandler.java:109`；`pipeline/AssetTaskHandler.java:139`；`pipeline/split/ChapterRebuildService.java:23`。

`checkStop()` 只检查 STOPPING/STOPPED，不比较 Task claim_token，也不拒绝被回收后的 PENDING、另一个 Worker 的 RUNNING 或 FAILED。进度写入没有 claim_token 条件。Task 心跳续租影响行数为 0 时也只打印日志。

Item 的提交只校验 Item token，没有关联 Task 当前 ownership。旧 Task 还持有 Stage 锁、替代 Runner 尚未接管 Item 时，旧 Item token 仍可能有效。SPLIT/ASSET 的拆话重建、资产合并及链式入队则没有 Item fencing。

**后果**：Task 已被 WatchDog 撤销，旧 Worker 仍可能写进度、提交图片、重建话和创建后续任务。严重时旧 SPLIT 的迟到重建会删除后来已经生成页面的话。

**建议**：Runtime 绑定 claim_token，并在步骤检查、进度 SQL、关键业务提交和链式入队验证所有权；明确 Task 与 Item 接管的原子边界。SPLIT/ASSET 的正式写入也要有执行围栏。

**验收**：撤销 A 的 Task lease 后，A 的所有正式写入和链式入队被拒；B 的结果与计数不变。验证不能只调用 `commitFenced()` 的 mock 单测。

### A09 — 自动重试没有增长，最大次数形同虚设

**位置**：`task/TaskWatchDog.java:67`；`repository/TaskMapper.java:75`。

看门狗调用 `requeueRevoked()`，其 SQL 没有 `retry_count = retry_count + 1`。虽然旧的 `requeueZombie()` 包含递增，但当前 handle 没有使用它。日志打印 `retryCount + 1` 不代表数据库真实增加。

**建议**：在同一 CAS 更新中递增计数，统一所有自动回收路径；清理无用的旧 SQL，避免路径再次分裂。

**验收**：配置 max_retry_count=N，连续超时后真实计数逐次递增，并最终 FAILED；双看门狗竞争只增加一次。

### A10 — 停止和人工操作缺少状态 CAS，STOPPING 可能被误判僵尸

**位置**：`service/TaskService.java:108`、`:132`、`:178`；`repository/TaskMapper.java:26`、`:41`、`:55`。

stop 先查询状态，随后按 ID 更新；retry/delete 也没有把检查时的状态放进最终写操作。并发恢复、领取或完成可能发生在两步之间，例如 stop 读到 RUNNING，Worker 已 SUCCESS，stop 再把它改成 STOPPING。

另一个缺口是心跳只更新 status=1。任务进入 STOPPING 后，即使 Worker 正在等待 AI 返回，心跳也不再刷新；固定 90 秒的 STOPPING zombie 扫描会把存活任务标为 STOPPED。Item 的迟到提交权限没有同时撤销。

`finishTask()` 还允许从 STOPPING 写 SUCCESS/FAILED；未做最后 stop 检查的非 Item Handler 有可能覆盖用户停止意图。

**建议**：所有状态转换使用明确的原状态 CAS；定义停止期间的续租/收尾规则，活着的 Worker 与死 Worker 分开处理；正常完成和停止竞争必须有确定结果。

**验收**：stop 与 claim/finish/resume/retry/delete 交错后状态合法；存活 STOPPING Worker 不被当作失联；死 Worker 最终 STOPPED；终态之后无迟到业务写入。

### A11 — PAUSED 仍没有完整产品和接口闭环

**位置**：`task/TaskStatus.java:34`；`service/TaskService.java:132`、`:178`、`:292`；`controller/TaskController.java:55`；`frontend/src/api/tasks.ts:12`、`:50`；`frontend/src/components/GenerationWorkbench.tsx:70`；`frontend/src/pages/admin/TaskMonitor.tsx:163`。

PAUSED 不应被 Worker 调度，但需要占用业务去重槽；当前多个调用方把“调度活跃”和“占用槽”混用。PAUSED 可以普通 retry（重置计数）及 delete，stop 又拒绝它；ensureUniqueActiveTask 不查询 PAUSED。

前端状态表无 7、API 无 task resume 方法，任务中心/管理监控会显示未知或提供重试。工作台也把暂停任务当作不活跃，可能重新开放开始生成。

后端有 `TaskService.resume()`，但 `TaskController` 没有对应单任务 resume 路由；目前只有项目级恢复入口。

项目级恢复还有收尾竞态：`controller/ProjectController.java:127` 先恢复 Stage，再查询 PAUSED Tasks；原 Runner 已识别暂停但仍在 drain 时，Task 尚是 RUNNING，查询不会恢复它。旧 Runner 随后把 Task 写成 PAUSED，就出现“恢复返回成功/0 个，但稍后任务才进入暂停”的错位。

**建议**：拆分“可调度”“占用槽”“终态”“可恢复”等状态语义；PAUSED 允许 resume/stop；完整添加前后端状态 7 和恢复接口；明确暂停请求、收尾完成、可恢复的顺序，处理 drain 期间提前恢复。

**验收**：暂停后无法创建冲突任务；禁止普通 retry/delete；可停止；同 Task 恢复；工作台、任务中心、管理员监控显示和动作一致。

### A12 — 同 Task 恢复仍重画已成功内容，进度被清零

**位置**：`pipeline/BatchTaskHandler.java:117`、`:149`、`:216`、`:236`；`pipeline/SheetTaskHandler.java:59`、`:163`；`pipeline/PageTaskHandler.java:54`；`pipeline/PostProcessTaskHandler.java:48`；`task/TaskRuntime.java:27`。

TaskService 保留了原 Task/payload，但 Handler 恢复后又执行“首次请求”的初始化：带 force 的 BATCH 重置全部目标 Items，手动素材任务重新 force reset 所选资产，单页和后处理也会再次重置。`runtime.begin()` 同时清空成功和失败计数。

**触发**：forceImage=true 的 10 页任务完成 6 页后暂停；resume 保留同一个 Task，却把那 6 个 SUCCESS Item 也重置，重新调用 AI。默认的手动素材任务也存在这个问题。

**建议**：将“接受一次用户请求并建立执行计划”与“恢复该执行计划”分开；force 意图只在首次规划时应用；从持久化计划和 Item 结果恢复计数，不重新初始化已完成单元。

**验收**：部分完成后暂停/恢复，成功页及资产 AI 调用数不增加；进度不会清零；payload 不变、Task ID 不变、原 scope 不变。

### A13 — 脚本更新后的过期图片不会自动重跑

**位置**：`service/PageService.java:75`；`pipeline/BatchTaskHandler.java:227`；`pipeline/PipelineStageService.java:173`、`:239`；`pipeline/LayoutTaskHandler.java:131`。

脚本版本增加后，BATCH 的 needGen 确实选中该页，但 `createItems()` 跳过已经存在的 SUCCESS Item，随后只 reset FAILED，因此 Runner 没有 PENDING Item 可领。已有布局的 SUCCESS Item 也不会因为版本过期重新排队；独立 LAYOUT 同步只检查 URL 是否为空。

`skipGenerated=false` 同样不保证重画：Item 可能仍然 SUCCESS，即使重新排队，`PageGenerationService` 的 fresh 检查仍可能直接复用旧图。

**建议**：执行计划按输入版本判断 Item 是否还能复用；过期结果精准重排；明确 skipGenerated=false 与 forceImage/forceLayout 的产品语义并统一到 Handler。

**验收**：成功页修改脚本后，普通 BATCH 更新布局及成品版本；其他新鲜成功页不产生额外费用；关闭跳过已有成品时行为与 UI 文案一致。

### A14 — 版本提交、完成状态和发布校验没有统一

**位置**：`pipeline/PageGenerationService.java:97`；`pipeline/LayoutGenerationService.java:57`；`pipeline/StageItemCommitService.java:58`；`pipeline/ProjectCompletionService.java:36`、`:73`；`pipeline/PublicationService.java:124`；`pipeline/PageTaskHandler.java:85`。

至少有三处不完整：

1. AI 在处理旧脚本版本时，用户可以修改脚本。提交仅校验 Item token，不验证当前页面输入版本是否仍与生成时相同。
2. 完成重算和发布校验只看 GEN_SUCCESS/URL，没有要求 image_script_version 与当前 script_version 一致。旧图仍可能被算作完成并允许导出。
3. 单页 PAGE 成功后没有调用话/项目完成重算；修复 BATCH 失败页后，Chapter/Project 可持续停留在部分失败。新增、删除及修改页面也没有完整的状态失效闭环。

**建议**：提交时检查输入版本；统一“可用成品”的判定；页面变更、单页修复、BATCH 完成均触发正确范围的完成重算。发布读取稳定版本快照，避免校验与 manifest 构建之间变化。

**验收**：旧版本生成结果不能被标为当前版本完成；过期图不能通过发布 Gate；单页修复后项目状态正确；发布包的图片、脚本版本及文本层一致。

### A15 — “重新生成本话脚本”实际没有重新生成

**位置**：`controller/ChapterController.java:45`；`service/ChapterService.java:70`；`pipeline/ScriptTaskHandler.java:64`、`:69`、`:90`、`:115`。

入口只创建带 chapterId 的 SCRIPT Task，没有创建或重置该话 SCRIPT Item；Handler 不使用 task.chapterId 限定范围，而是重排项目 FAILED，运行全项目 Items。该话已有 SUCCESS Item 时不会执行；即使 Item 排队，Chapter 状态 SCRIPT_READY 以上还会直接跳过。

修改话原文会回退 Chapter 为 PENDING，但没有使 SUCCESS Item 失效。用户点击重新生成后，任务可能直接成功，旧页面原封不动。

**建议**：显式设计话级脚本重生成请求、输入版本和 force 语义；精准创建/重置目标 Item；使用章节 Scope。重建页面前处理已有图片、文本层和引用的影响。

**验收**：已生成话点击重新生成会执行目标话的新脚本；修改原文后生成反映新内容；其他话零调用、零修改；并发操作不能意外删除后来写入的页面。

### A16 — CLEAN 和 REPAINT 均执行上色

**位置**：`pipeline/CleanTaskHandler.java:23`；`pipeline/RepaintTaskHandler.java:23`；`pipeline/PostProcessTaskHandler.java:43`；`pipeline/PostProcessService.java:46`。

两个 Handler 的 `op()` 都返回 `OP_COLORIZE`。因此它们使用 COLORIZE Stage、上色提示词和单张原图。局部重绘不会走遮罩/重绘提示词分支；Controller 预建的 CLEAN/REPAINT Item 也可能无人处理。

**建议**：正确绑定 CLEAN/REPAINT 操作、Stage 和记录类型；从入口到 AI 请求验证对应参数，不能只测试 Service 的正确分支。

**验收**：CLEAN 使用清晰化提示词；REPAINT 提交原图和遮罩以及用户提示词；对应 Stage Item 进入终态；不污染 COLORIZE。

### A17 — 不同操作的 Stage fencing 不能防止同页互相覆盖

**位置**：`pipeline/ConcurrentStageRunner.java:103`；`pipeline/PostProcessTaskHandler.java:43`；`pipeline/PostProcessService.java:78`；`pipeline/PageGenerationService.java:97`。

锁和 token 的粒度是 project+stage / stage item。IMAGE、COLORIZE、CLEAN、REPAINT 可以各自合法持有 token，同时修改同一个 page.generated_image_url 和 generate_records。记录追加使用处理开始时的旧 JSON 快照，最后提交者会覆盖先提交者的结果及历史。

修正 A16 后，不同操作之间的竞争仍然存在，不能认为修正操作名就完成了后处理收口。

**建议**：为同一页面的正式图片修改建立统一串行规则，或使用页面结果版本做提交 CAS。后处理绑定输入图片版本，提交时拒绝基于已经被替换图片的旧结果；历史独立追加或在业务行锁内读取最新记录。

**验收**：同时出图、上色、清晰化和重绘时，有明确的冲突/排队语义；不覆盖新结果，不丢历史。

### A18 — 生成图片转存仍走不受保护的整图下载

**位置**：`ai/AiService.java:95`；`storage/OssStorageService.java:65`、`:145`；`pipeline/PublicationService.java:235`。

新的 RemoteImageFetcher 只接入发布 ZIP。AI 返回的图片 URL 仍由 OssStorageService 的 HttpClient 下载，自动跟随重定向，没有内网地址检查、响应 MIME 限制或图片字节上限，使用 `BodyHandlers.ofByteArray()` 整图入内存。

AI 返回的 data:base64 同样直接整体解码，没有本地大小/MIME 上限。它是外部服务返回的数据，不能因为不是用户直接提交而跳过限制。

**风险边界**：恶意/异常 AI 返回地址或被替换的上游可能让后端访问内网；大响应及高并发导致堆内存压力。这里没有声称任意普通用户可直接指定转存目标。

**建议**：生成转存和导出统一使用受限制的拉取路径；OSS 接受有限流；base64 在解码前后检查体积并验证图片格式。

**验收**：URL、redirect 和 base64 均有限制；内网跳转被拒；高并发下载内存可控。

### A19 — RemoteImageFetcher 的安全边界仍可绕过

**位置**：`pipeline/RemoteImageFetcher.java:99`、`:110`、`:124`。

白名单命中就 return，完全跳过 DNS/IP 校验。默认 IP 检查依赖 InetAddress 的 local 分类，未覆盖 IPv6 ULA。校验 DNS 与真正建立连接分两次解析，仍有 DNS 变化的时间窗口。

隔离探针仅调用当前 `validateUri()`，没有向内网发送 HTTP，实际输出：

```text
whitelisted localhost=ACCEPTED
default localhost=禁止访问内网图片地址: localhost
IPv6 ULA fd00::1=ACCEPTED
```

另有格式校验缺口：响应未提供 Content-Type 时直接放行；只检查响应头，不验证图片内容。

**建议**：白名单和 IP 校验共同执行，除非另有明确隔离的可信私网存储模式；完善地址范围判断；确保连接目标与验证目标一致并保留正确的 TLS host 校验；校验图片魔数。可信私网模式若确有需求，应单独审核其访问边界。

**验收**：白名单 localhost/private IP 仍被拒；IPv4/IPv6 内网及 redirect 被拒；受控 DNS 变化测试通过；真实图片类型不匹配被拒。

### A20 — 实际批量导出仍按总包大小占用内存

**位置**：`controller/AdminExportController.java:69`、`:74`、`:79`、`:92`、`:99`、`:118`。

`writeZip()` 内部虽然流式处理图片，但调用方把每部 ZIP 写入 ByteArrayOutputStream，再复制为 byte[] 放进 packages。外层 ZIP 再写入另一个内存缓冲并返回 byte[]。内存仍随全部作品包大小增长，且有复制峰值。

外层 `packages.forEach` 对 ZIP 写入异常使用空 catch。重复项目 ID 会覆盖同名 packages，却仍逐次计入 success；其他写入错误也可能导致 summary 声称成功但包缺失。

本轮没有发现对外 Controller 使用 StreamingResponseBody。Phase 8.8 提交标题中的流式 HTTP 结果没有体现在实际出口。

**建议**：去重并限制批量 ID；逐部写响应流或有上限的临时文件，不在内存保存所有包；大任务采用受控异步导出。summary 只记录真正写入成功的作品，禁止吞掉错误。

**验收**：大包及并发导出内存有上界；全部条目可解压；重复 ID 的数量正确；失败清单与最终包内容一致；客户端中断可释放资源。

### A21 — Redis 短暂故障可能永久杀死 Worker

**位置**：`task/TaskWorkerPool.java:126`；`task/TaskQueue.java:38`。

poll 仅捕获 InterruptedException，`removeMarker()` 位于执行异常保护块之外。Redis 操作的运行时异常可直接退出 workerLoop；Future 保留异常但没有重启监督。poolSize 只记录目标数量，不统计存活 Worker，`refresh(相同目标)` 直接返回。

**触发**：Redis 临时不可用时 Worker 的 poll 或 marker 删除失败。Redis 恢复后，即使补偿调度重新入队，消费线程已经退出，任务仍可能永久排队。

**建议**：调度循环覆盖队列和 marker 的异常，使用有上限的退避；监控及补充意外退出的 Worker；区分正常缩容/停机与故障退出。

**验收**：Redis 停止再恢复后，Worker 存活数恢复，MySQL PENDING 最终执行；marker 删除失败也不永久丢失消费能力。

### A22 — 用户并发限制在长任务上失效

**位置**：`task/RedisConcurrencyLimiter.java:92`；`task/TaskWorkerPool.java:174`；`resources/db/migration/V1__baseline_schema.sql:441`。

用户 Task permit 固定 10 分钟，没有续期，而 Task 默认最大单次执行时间为 3600 秒。长漫画 BATCH 超过 10 分钟仍在运行，但其用户许可可以被其他获取方清理并重新发放。

**建议**：Task permit 与当前执行租约绑定续期，或由带租约的事实源判断占用；实例崩溃时仍须最终释放。AI permit 持有范围包括 OSS 转存，也应验证 TTL 是否覆盖整个操作。

**验收**：一个用户长任务运行超过 10 分钟后仍计入上限；多实例下不超发；崩溃后无永久占用。

### A23 — 页面和文本层保存失败会留下半更新数据

**位置**：`pipeline/TextLayerService.java:86`、`:140`、`:158`、`:166`；`service/PageService.java:65`。

文本层 Service 没有类级或方法级事务。saveTextLayer 边验证边写入：第一个元素已经保存后，第二个元素缺 position 或重复 UID 会返回 400，但第一项变更不会整体回滚。reset 先删全层，再初始化；插入失败时原布局已经丢失。

页面脚本更新、script_version 增加和素材绑定重建也是多个非整体事务操作，中间失败会产生文本、版本、引用不一致。

**建议**：先完整校验请求，再以短事务提交整组变更；页面文本与版本及绑定更新保证原子性；并发编辑采用版本冲突检查，避免不同客户端静默覆盖。

**验收**：后一个元素非法或数据库中途失败，整个文本层保持原样；reset 失败保留旧层；页面文本、版本和绑定一起成功或一起失败。

### A24 — 初始管理员固定密码缺生产隔离

**位置**：`config/AdminBootstrap.java:22`。

只要库里没有 ADMIN，就自动创建固定 `admin / admin123`，并在日志输出密码。代码没有开发 profile 限制、生产显式 bootstrap 开关或首次配置凭据。

**建议**：生产环境显式注入首次管理员凭据，或使用一次性初始化流程；开发默认账号仅用于开发环境；避免日志记录可用密码，并保证双实例初始化安全。

**验收**：生产空库不自动生成公开固定密码；无凭据时给出明确初始化状态；双实例引导不重复插入或异常启动。

### 测试和 CI 的实际缺口

本地发现 13 个后端测试类，未发现 Testcontainers 依赖及真实 MySQL/Redis 集成测试。仓库根的 `.github/workflows/ci.yml` 运行后端 `mvn test` 和前端构建，没有数据库/Redis 服务及迁移检查。

`StaleCommitFencingFailureInjectionTest` 直接 new 提交 Service 并 mock Mapper，因此不经过真实 Spring 事务、行锁或 Mapper 注册。这类测试有价值，但目前不能证明数据库级 fencing 和 rollback。

其名为 F5 的测试实际验证“最新 Attempt 成功提交”，并没有执行文档中“AI/OSS 成功后、DB commit 前 crash”；F6 验证“已成功 Item 拒绝旧 token”，并没有完成“业务已提交、Task 未终态时 crash 后恢复”的完整流程。**测试名称与 Phase Gate 不是同一层面的证据。**

本轮没有验证远端 Actions 是否实际运行或是否被设置为合并必要检查。新 workflow 在本地状态中属于既有未跟踪内容，不能据文件存在宣称 GitHub CI 已启用。
