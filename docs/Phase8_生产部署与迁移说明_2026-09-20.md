# Phase 8 生产部署与迁移说明

本文适用于包含 `V8_1_0` 至 `V8_1_4` 迁移的版本。数据库变更由 Flyway 执行，部署时不要手工修改已发布迁移，也不要直接删除新增列或计划表。

## 1. 发布前检查

1. 备份 MySQL，并实际验证备份可恢复。
2. 确认 Redis 与 OSS 可用，OSS 凭据具备读、写、删除 `exports/` 目录对象的权限。
3. 在管理后台核对 AI 三个通道、任务租约、心跳间隔、执行时限、用户并发、导出配额和产物有效期。
4. 停止新任务进入队列，等待正在运行的旧版本 Worker 完成；无法完成的任务先停止，不能让旧代码与新代码同时写新的所有权和计划字段。
5. 在测试环境执行 `mvn -B verify`，并确认 GitHub 的 `backend-verify` 与 `frontend-checks` 均通过。

## 2. 迁移内容

| 版本 | 内容 |
|---|---|
| `V8_1_0` | Stage Item 增加 Task 所有权字段与索引 |
| `V8_1_1` | Project、Task 增加持久化暂停意图和控制版本 |
| `V8_1_2` | Task 固定执行计划、计划单元、页面图像 revision、APP fallback 字段 |
| `V8_1_3` | 异步导出产物表、过期索引和 Task 关联 |
| `V8_1_4` | 非敏感生产默认配置与稳定风格预设键 |

`V8_1_4` 只插入缺失配置，不覆盖已经存在的运营值。AI 地址、模型、API Key 和 OSS 密钥默认留空。初始管理员也不会由迁移创建。

## 3. 推荐发布顺序

1. 保持旧 Worker 已停止领取任务。
2. 启动一个新版本实例，让 Flyway 完成迁移；检查 `flyway_schema_history` 到 `8.1.4` 且无失败记录。
3. 检查 `/api/admin/monitor/overview`，确认 Worker 数量、队列补偿、心跳失败、所有权丢失和 permit 续租失败没有异常增长。
4. 新版本启动后会为旧的 PENDING/PAUSED Task 建立固定计划。范围可安全恢复的任务复用已成功 Stage Item；范围不明确的旧任务会失败并给出“需要人工处理”的错误，避免误扩大到全项目。
5. 先开放少量项目，验证暂停/继续、单话和多话范围、单页重画、发布校验与异步导出，再恢复全部流量。

## 4. 关键配置

| 配置 | 默认值 | 约束/用途 |
|---|---:|---|
| `task_max_execution_seconds` | 3600 | 单次 Task Attempt 最大执行秒数，60—86400 |
| `task_lease_seconds` | 90 | 数据库执行租约秒数，30—600 |
| `task_heartbeat_interval_seconds` | 30 | 必须小于租约，建议不超过租约的三分之一 |
| `task_heartbeat_threads` | 2 | 心跳线程数，1—8 |
| `task_permit_ttl_seconds` | 120 | 用户并发许可 TTL，心跳成功后续租 |
| `export_max_projects` | 50 | 单个异步导出任务作品数上限 |
| `export_max_bytes` | 1073741824 | 单个导出包最大字节数 |
| `export_artifact_ttl_hours` | 168 | 成功产物与检查点保留时间 |

AI 通道许可的 TTL 由对应 `ai_*_timeout` 再加清理余量计算。缩小并发上限不会中断已有合法许可，只会暂停发放新许可。

## 5. 运行验证

发布后至少完成以下检查：

- 创建单页、单话、多话与整部任务，确认目标范围外的 Item 和失败预算不变。
- 在任务执行中暂停并立即继续，确认仍是同一 Task、同一 payload，已成功页不重复调用 AI。
- 执行中修改页面脚本或成品图，确认旧请求因版本冲突被拒绝，最新结果不被覆盖。
- 修改对白后直接发布，确认 Gate 拒绝过期文本层；同步后 manifest 同时包含文本层、正文 fallback 和版本字段。
- 发起批量导出，确认 HTTP 只返回 Task；成功或部分成功后通过受控接口下载，过期、停止或失败任务不可下载。
- 中断 Redis 后恢复，确认 Worker 数量恢复、PENDING Task 由数据库扫描补偿，未绕过用户并发限制。

## 6. 监控与告警

重点观察：任务 heartbeat 失败、ownership lost、stale commit rejected、版本冲突、暂停 drain 时长、Worker 期望/存活/收缩数量、队列补偿、permit used/max/renew failure、导出失败和导出字节数。Task ID、Page ID 和 token 只进入日志，不作为高基数指标标签。

建议为以下情况设置告警：连续心跳失败、Worker 存活数低于期望、PENDING 长时间不下降、许可续租失败、stale commit 突增、导出失败率或过期清理失败持续增长。

## 7. 回退策略

数据库采用向前修复。应用回退前必须确认旧版本不会绕过新的 Task/Item 所有权、页面 CAS 和固定执行计划；无法确认时不要把旧版本重新接入写流量。

如果新版本应用异常：停止领取新任务，保留数据库和 OSS 新增数据，修复应用后重新部署。新增列和表与旧数据共存，不要删除 `task_plan_unit`、`export_artifact` 或版本字段。导出临时/过期对象由清理任务处理，必要时按 `export_artifact` 记录人工核对后删除。

## 8. CI 与分支保护

工作流 `.github/workflows/ci.yml` 在 PR 和 main push 时运行：

- `backend-verify`：Java 17、Maven verify、MySQL/Redis Testcontainers。
- `frontend-checks`：Node 20、npm ci、类型检查、Vitest、Vite build。

仓库管理员需要在 GitHub main 分支保护中把这两个名称配置为必需检查。工作流文件本身不会自动启用分支保护。
