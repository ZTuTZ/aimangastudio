## 1. P1：Redis 许可写入与释放使用不同编码

位置：`server/src/main/java/com/aimanga/v2/task/RedisConcurrencyLimiter.java:57,70,94-96`。

获取与续租使用 StringCodec，ZSET 中存的是原始 token 字符串；释放调用没有传 Codec，使用 Redisson 默认编码。当前项目没有统一 StringCodec 配置，释放时编码后的 member 与写入值不一致，ZREM 无法移除许可。

影响：已完成任务继续占用名额直到 TTL；默认用户许可约 120 秒，AI 许可按 timeout + 120 秒计。短任务连续执行会出现排队、吞吐骤降或等待许可超时。

修复：释放也显式使用 StringCodec，或用同一 StringCodec Lua 执行 ZREM。不要依赖全局默认 Codec。

验收：max=1，获取 A → 释放 A → 立即获取 B，必须成功；分别覆盖用户许可、AI 许可和重复释放。现有 Redis 集成测试没有调用 release，故未发现此问题。

## 2. P1：素材任务创建存在事务自调用，失败后可能残留无计划任务

位置：`service/TaskService.java:316-342,354-372,389-413`；调用入口 `pipeline/MaterialGenerationService.java:96`。

ensureUniqueActiveTask/enqueueUnique 在同一个 Bean 内直接调用标注 @Transactional 的 createSystemTask，绕过 Spring 事务代理。素材入口本身也没有外层事务。save(task) 与另一个 Bean 的 initializePlan 因而不是同一事务；计划初始化报错时，已插入的 PENDING Task 不会一起回滚。数据库补偿还可能在计划完成前看到任务。

此外，普通 create 使用项目行锁，这两个入口使用独立 Redis 锁，准入入口没有统一串行化机制。

修复：将准入、项目锁、Task 插入、计划初始化放进独立事务 Bean，并让所有创建入口使用同一机制；事务提交后入队。

验收：真实 Spring 代理环境中令 initializePlan 抛异常，Task/计划/Item 必须全部回滚；并发调用普通创建与素材创建，不得产生重叠活跃任务。纯 Mockito 服务测试不能证明事务有效。

## 3. P1：部分成功导出重试后仍下载旧包

位置：`pipeline/ExportArtifactService.java:35-37,52-65`；`pipeline/ExportTaskHandler.java:158-178`。

TaskService.retry 允许 PARTIAL 任务重试失败单元。旧产物已经 ACTIVE，reserve 原样返回它；新 ZIP 生成后 activate 会删除新文件并返回旧产物。随后 Task.result 却使用新计算的 bytes、sha256、success 等信息。

触发：两本书首次只导出一本，修复失败原因并重试原任务。界面可能显示两本成功，下载文件仍只有一本，摘要与实际文件不一致。

修复：产物引入版本/执行代次；新产物成功后原子切换引用，再清理旧文件。Task.result 与产物记录必须来自同一已发布版本。

验收：PARTIAL → retry → SUCCESS，实际 ZIP、summary、下载响应大小和 SHA256 全部对应新包。

## 4. P1：导出失败清理与同任务重试不兼容

位置：`repository/ExportArtifactMapper.java:16-31`；`pipeline/ExportArtifactService.java:35-67,100-109`；`repository/TaskPlanUnitMapper.java:55-58`。

清理会处理 FAILED/STOPPED Task，删除成功 checkpoint 并将产物置 EXPIRED；但 reserve 总是复用同 task_id 的记录，activate 仅允许 BUILDING → ACTIVE。人工重试只重开 FAILED 单元，仍然保留 SUCCESS 单元引用已删除的 checkpoint。

触发：导出在最终上传阶段失败 → 清理执行 → 重试同一任务。可能读取不到 checkpoint，或最终激活永久返回 409。清理扫描与人工重试之间也没有排他保护，可能在任务已恢复后删除文件。

修复：明确可重试数据保留期；重试与清理采用状态/版本 CAS；checkpoint 缺失时重建相应单元；允许为新执行代次预留新产物。

验收：失败清理后重试、停止后重试、清理扫描后立即重试，均不得复用失效文件或删除在用文件。

## 5. P1：最终导出产物发布缺少 Task 所有权校验

位置：`pipeline/ExportTaskHandler.java:158-180`；`repository/ExportArtifactMapper.java:16-21`。

activate 在 runtime.checkStop 之前调用，SQL 只检查产物 status=0，不检查 Task claim_token 或 lease。失去所有权的旧 Worker 仍可抢先激活产物；之后对 Task.result 的有所有权更新失败，也不会撤销已激活产物。新 Worker 会走复用 ACTIVE 旧产物的分支。

修复：激活产物及绑定任务结果必须在事务内校验并锁定当前 Task 所有权；对象上传在事务外，失败所有权校验后清理该次上传。仅提前调用 checkStop 不能消除检查与写入之间的竞态。

验收：A 在上传后阻塞 → 撤销 A、B 接管 → 释放 A，A 不得激活产物、替换下载引用或删除 B 的文件。

## 6. P1：删除导出任务会遗失文件清理索引

位置：`service/TaskService.java` 的 delete；`db/migration/V8_1_3__export_artifact.sql` 的 ON DELETE CASCADE；`repository/ExportArtifactMapper.java` 的 selectCleanupCandidates。

删除终态 Task 直接 removeById；外键级联删除 export_artifact。清理任务依赖该表并 JOIN task，删除后再也无法发现对应最终 ZIP 和 checkpoint，造成对象存储泄漏。

修复：先持久化独立于 Task 的清理记录，再删除任务；或软删除并保留清理元数据，文件清理成功后再物理删除。不要把远程删除与数据库级联当作同一个原子操作。

验收：删除已成功导出任务，模拟 OSS 删除暂时失败，后续清理仍可重试，最终文件和 checkpoint 均被回收。

## 7. P1：导出额度不能支持文档的 6GB 验收，且限制检查过晚

位置：`pipeline/ExportTaskHandler.java:84-93,125-128,193-196`；`service/ConfigService.java` 的 getInt。

export_max_bytes 通过 Integer.parseInt 读取，超过 2,147,483,647 的配置会解析失败并退回默认 1GiB，无法配置文档要求的 6GB 批量导出。单本 ZIP 先完整写盘后才检查大小；下载 checkpoint 也先完整落盘再检查，限制不能防止磁盘被超大输入写满。

修复：额度使用 long 并严格校验配置；写盘/复制流中增量计数并及时终止；提供临时磁盘总量和并行导出预算。

验收：配置超过 6GB 的有效额度，在固定堆下导出 20×300MB；超额时在写入阈值附近终止；磁盘不足不发布成功链接。

## 8. P2：监控读取会按本机时间删除 Redis 许可

位置：`task/RedisConcurrencyLimiter.java:139-146`。

获取和续租使用 Redis TIME，但 aiOccupancy 使用 System.currentTimeMillis 清除成员。应用实例时间领先 Redis 时，查询监控本身就可能删掉仍有效的许可，随后新请求突破实际并发上限。

修复：使用 Redis TIME 的原子脚本统计；最好让监控只查询有效成员数量，不修改限流状态。

验收：应用时钟领先 Redis 时查询监控，不得删除有效许可或使获取超额成功。
